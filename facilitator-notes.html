Facilitator Notes

Issues in the order Dennard will hit them scrolling top to bottom through bad.html. Each maps to a WCAG 2.1 success criterion and its fix in good.html.

1. Logo image alt text is the filename

Bad:
alt="logo_1.svg" — screen reader announces "logo underscore one dot s v g, image," meaningless.
WCAG:
1.1.1 Non-text Content
Fix:
alt="Let's Play home" — describes purpose, not filename.

2. Navigation menu is duplicated in the DOM

Bad:
Two identical nav lists exist; one is hidden with an off-screen position hack instead of hidden/display:none, so it stays in the accessibility tree. Dennard swipes through the same four links twice before reaching content. (Inspired by a real, verifiable issue found on a live disability-sport site during research for this workshop.)
WCAG:
4.1.1 Parsing 2.4.1 Bypass Blocks
Fix:
One nav in the DOM; the hidden attribute actually removes it from the accessibility tree when closed.

3. Hamburger menu is a <div>, not a button

Bad:
A styled <div> with role="button", a tabindex, and a keydown handler bolted on — enough that AT actually stops on it (both Tab and swipe/linear navigation), so Dennard can still reach and open it. But it's still not a real button: no accessible name, no aria-expanded state. It announces as bare "button", with no clue what it does or whether it's currently open.
WCAG:
4.1.2 Name, Role, Value
Fix:
Real <button> with aria-expanded, aria-controls, and a descriptive aria-label.

4. Hero "heading" isn't a heading

Bad:
Big bold text is a <div> styled to look like a headline. Dennard's rotor/heading navigation won't find it — and there is no real <h1> on the page at all.
WCAG:
1.3.1 Info and Relationships 2.4.6 Headings and Labels
Fix:
Real <h1>, one per page.

5. Heading levels skip straight to h4

Bad:
Every section heading is an <h4> with nothing above it — navigating by heading level makes no structural sense.
WCAG:
1.3.1 Info and Relationships
Fix:
Logical h1 > h2 > h3 hierarchy matching visual nesting.

6. Event list has no list semantics — unclear grouping

Bad:
The three events are just a stack of <div>s, not a <ul>/<li> list. A screen reader never announces "list, 3 items" and gives no boundary between one event's details and the next — combined with the identical "Register" links (below), Dennard has no reliable way to tell how many events exist or which date/status belongs to which title.
WCAG:
1.3.1 Info and Relationships
Fix:
Real <ul>/<li> markup — AT announces the item count and groups each event's title, status, and link as one unit.

7. Event status is a colour-only dot

Bad:
"Spots available" vs "Fully booked" is shown only as a small red or green dot — invisible to a screen reader, and the red/green pairing sits on the confusion line for the most common forms of colour vision deficiency.
WCAG:
1.4.1 Use of Color
Fix:
Icon and visible text label ("● Spots available"), each with sufficient contrast on its own badge background. The dot itself is wrapped in <span aria-hidden="true"> — it's purely decorative once the text label is there, and without hiding it a screen reader announces "black circle Spots available" on every card.

8. Dates written in ambiguous numeric slash format

Bad:
Tue, 4/5, 11/5, 18/5 — a screen reader doesn't recognise these as dates, so it reads the digits and punctuation literally ("four slash five") instead of a month name. The first date is also genuinely locale-ambiguous, not just badly read aloud: 4/5 could mean 4 May or 5 April, depending entirely on whether the reader assumes DD/MM or MM/DD (Dennard's own team splits on this).
WCAG:
1.3.1 Info and Relationships
Fix:
Spelled-out month ("Tue, 10 Mar"), wrapped in a semantic <time datetime="2027-03-10"> element so both the visible text and the underlying value are unambiguous.

9. Low-contrast text throughout

Bad:
Event dates, the testimonial quote, and footer links all use light grey/blue on white, roughly 2.3–2.6:1 contrast.
WCAG:
1.4.3 Contrast (Minimum)
Fix:
All body text at or above 4.5:1 against its background (checked per colour pair in good.css).

10. "Register" / "Read More" repeated identically

Bad:
Every event card and news item uses the exact same link text. Out of context (e.g. Dennard's links list), they're indistinguishable.
WCAG:
2.4.4 Link Purpose (In Context)
Fix:
Each link's visible text names what it leads to, e.g. "View details for Tuesday Stadium Run."

11. Focus indicator removed site-wide

Bad:
* { outline: none; } — even the links/inputs that are keyboard-focusable show no visible focus state.
WCAG:
2.4.7 Focus Visible
Fix:
A clear, high-contrast :focus-visible outline restored on every interactive element.

12. Photo alt text is the filename

Bad:
alt="IMG_2041.jpg" on the athlete spotlight photo.
WCAG:
1.1.1 Non-text Content
Fix:
Meaningful alt text describing the image, e.g. "Portrait of a smiling Let's Play club member."

13. Auto-advancing news carousel with no pause control

Bad:
Rotates every 1.2 seconds via JS, forever, with no way to pause, stop, or hide it. It now has slide-picker dots too, but they're bare <button>s with no text, aria-label, or aria-current, and picking one by hand doesn't pause the rotation either — it gets yanked to the next item a moment later regardless.
WCAG:
2.2.2 Pause, Stop, Hide 4.1.2 Name, Role, Value
Fix:
Replaced with a simple static list — the safest fix when a carousel isn't essential to the content.

14. Icon-only footer links with no accessible name

Bad:
Social links are real Facebook/Instagram/YouTube logo icons (inline SVG), but with no <title> in the icon and no aria-label on the link — a screen reader announces three bare, identical "link"s with no way to tell them apart.
WCAG:
4.1.2 Name, Role, Value 2.4.4 Link Purpose
Fix:
aria-label="Let's Play on Facebook" on the link, aria-hidden="true" on the now-decorative icon so it isn't announced twice.

15. Opening the menu never moves focus into it

Bad:
The menu opens as a fixed overlay on top of the rest of the page, but toggleMenu() never calls .focus() on anything, and none of the underlying content is made inert. The nav markup itself is appended at the very end of the DOM (a common real cause of this bug — an off-canvas panel moved there for stacking/z-index reasons). So the next Tab after the hamburger goes straight into the hero, events, spotlight, and everything else the panel is visually covering, long before it ever reaches the menu links sitting at the bottom of the page.
WCAG:
2.4.3 Focus Order
Fix:
On open, focus deliberately stays on the toggle button — its aria-expanded/aria-label change is announced right there, and because the nav sits immediately after the header in the DOM, the very next Tab moves naturally into the first link. On close, focus explicitly returns to the button in case it had moved further into the menu. See toggleMenu() in good.js.

16. Hero heading/CTA sit on a photo with no contrast safeguard

Bad:
Each hero carousel slide's background photo/gradient is a CSS background on .carousel-slide, and the heading and paragraph are placed directly on top of it in plain white text — no scrim/overlay behind them, no actual contrast check against what's underneath. Legibility depends entirely on which part of the busy photo (or which gradient) happens to sit behind each line.
WCAG:
1.4.3 Contrast (Minimum)
Fix:
The photo is a plain content <img> above the text, not behind it — heading/paragraph sit on the page's normal light background afterward, so contrast is unaffected by the image entirely.

17. Hero carousel never stops, and its controls aren't labelled

Bad:
The hero banner is now itself a 3-slide auto-advancing carousel — same missing pause/stop control as the news carousel further down (see issue #13), except this is the very first thing on the page and doesn't respect prefers-reduced-motion either. Navigation is dots-only (no arrows), and the three slide-picker dots are bare <button> elements with no text, no aria-label, and no aria-current on the active dot — a screen reader announces all three identically as bare "button", with no way to tell which dot goes to which slide. Picking a slide manually doesn't even pause the auto-advance — it gets yanked to the next slide 3.5s later regardless. Each event card now has its own small image carousel too, same dots-only pattern, same bare, unlabelled <button> dots.
WCAG:
2.2.2 Pause, Stop, Hide 4.1.2 Name, Role, Value
Fix:
Not yet built in good.html — the hero stays a single static image with real, labelled content, sidestepping both problems the way issue #16's fix already does.

18. Event card and news images have no alt attribute at all

Bad:
Every event card and news item has a real licensed photo now, but none of them have an alt attribute — not even alt="", it's just missing entirely. A browser falls back to announcing the raw src to a screen reader instead of nothing, which is arguably worse than a bad filename alt (issues #1 and #12) — and unlike a plain placeholder rectangle, these photos genuinely carry information a screen reader user is missing entirely (which sport, which venue, who's in it).
WCAG:
1.1.1 Non-text Content
Fix:
Real, descriptive alt text on every image in good.html, matching what's actually in each photo (e.g. "A wheelchair racing athlete in a helmet and racing wheelchair on an athletics track") rather than the event title already sitting next to it in visible text — a screen reader user gets the same picture a sighted user does, not just a repeat of the heading.

19. Registration form fields have no labels, and nothing shows what's required

Bad:
New page: bad-register.html, linked from every event card's "Register" button. Full Name, Email, and Phone are all placeholder-only — no real <label> for any of them. Required fields get a bare "*" appended to the placeholder, explained by a "* = required" line sitting on its own at the bottom of the form — the asterisk isn't programmatically tied to the fields it marks (no aria-required, no required attribute, not even adjacent text), so the association only exists visually, and vanishes from each field entirely the moment its placeholder disappears on input.
WCAG:
1.3.1 Info and Relationships 3.3.2 Labels or Instructions
Fix:
good-register.html — every field has a real <label> linked via for/id, and required vs. optional is called out in visible text right in the label (not colour alone), so it's exposed to a screen reader and doesn't disappear once a value is typed.

20. Date picker looks like radio buttons but has no semantics at all

Bad:
Same page — three date options ("Tue, 10/3" etc.) styled to look like a radio group, but built as plain <div>s with an onclick handler that swaps a CSS class. No role="radio", no aria-checked, no fieldset/legend grouping them, no name attribute linking them at all. A screen reader gets no indication of which date is currently selected, or even that picking one should deselect the others. (Inspired by real feedback: not being able to tell which date had actually been selected was one of the most disorienting parts of testing a site like this.)
WCAG:
4.1.2 Name, Role, Value 1.3.1 Info and Relationships
Fix:
good-register.html — a real <fieldset>/<legend> group of native, fully visible radio buttons sharing one name, each linked to its own <label>. A screen reader announces the group label ("Select the date you would like to attend"), how many options there are, and which one is checked; the browser handles the visual checked state, focus ring, and arrow-key navigation for free, no JS or custom styling required.

21. "I agree to Terms and Conditions" checkbox has no checkbox semantics

Bad:
Same page — styled to look like a checkbox, but it's a plain <div> with an onclick handler that swaps a CSS class. No real <input type="checkbox">, no role="checkbox", no aria-checked. A screen reader has no way to tell whether it's checked, unchecked, or even that it's a control at all.
WCAG:
4.1.2 Name, Role, Value
Fix:
good-register.html — a real <input type="checkbox"> with a linked <label>. A screen reader announces "checkbox, not checked" and the state updates as it's toggled, none of which a styled <div> can do on its own.

22. Submission confirmation is a silent toast

Bad:
Same page — submitting the form shows a toast ("Registration submitted!"), but it's just a plain <div> whose visibility is toggled by a CSS class, with no role="status" or aria-live region at all. A sighted user gets clear visual confirmation; a screen reader user hears nothing and has no idea whether the submission worked.
WCAG:
4.1.3 Status Messages
Fix:
good-register.html — the confirmation text lands in a role="status"/aria-live="polite" region instead of a plain toggled <div>. A screen reader announces it the moment it's set, the same instant a sighted user sees it appear.

23. Event date/time line reads as fragmented, punctuation-cluttered noise

Bad:
Each event card's meta line ("Tue, 10/3, 17/3, 24/3 · 6:30 – 7:30 AM · Stadium Waterfront Promenade") uses a literal middle-dot character as a visual separator with no markup hiding it from assistive tech, so a screen reader speaks it aloud as punctuation ("dot") between every segment.
WCAG:
1.1.1 Non-text Content 1.3.1 Info and Relationships
Fix:
Both good.html and good-register.html rewrite the whole line as one flowing sentence with no separators to hide at all: "Tuesdays, 4, 11 and 18 May, 6:30 to 7:30 AM, at Stadium Waterfront Promenade" — no <time> fragments, no middle dots, nothing for a screen reader to stumble on. good-register.html's per-event line is built from shared date/time/location data rather than hand-written, but produces the identical plain-sentence format.

24. "Verify you're human" is a drag-only slider with no keyboard path at all

Bad:
bad-register.html — a bot-check slider styled to look like a puzzle piece you drag across a track. It's built entirely on pointerdown/pointermove/pointerup: no role="slider", no aria-valuenow/min/max, no accessible name, and critically no keydown handler or even a tabindex — a mouse or touchscreen user can drag it, but a keyboard-only or screen reader user has no way to interact with it whatsoever. Worse, "Complete Registration" is greyed out (CSS opacity/cursor only, no real disabled attribute) until the slider is completed, so a screen reader still announces it as a perfectly normal, enabled button — clicking it does nothing at all, silently, with zero error message or explanation. A keyboard-only user is completely locked out of registering, full stop.
WCAG:
2.1.1 Keyboard 4.1.2 Name, Role, Value 3.3.1 Error Identification
Fix:
good-register.html swaps it for a Cloudflare Turnstile widget — non-interactive for most visitors (a background check, nothing to drag or click), and on the rare occasion it does need interaction, that's a single labelled, keyboard-operable checkbox rather than a puzzle. Turnstile is WCAG 2.2 AA-compliant. This demo uses Cloudflare's public, non-secret test site key (1x00000000000000000000AA, documented to always pass on any hostname) since this static site has no backend to verify a real token against — same limitation as the rest of the registration flow, which doesn't submit anywhere either. "Complete Registration" stays a plain, always-enabled button throughout.

25. "Register" for a fully-booked event looks disabled but isn't

Bad:
Wednesday Sunset Yoga's "Register" is greyed out and its click is blocked with onclick="return false" — a real, working fix for mouse and keyboard users alike, but a purely visual/behavioural one. No aria-disabled, no role change, nothing exposed to AT at all: a screen reader still announces it as an ordinary, enabled "Register" link, and only discovers it does nothing after activating it. The only hint anything's different is a colour-only status dot with a title attribute (hover-only, not reliably exposed) — there's no visible text anywhere saying why nothing happens.
WCAG:
4.1.2 Name, Role, Value 1.3.1 Info and Relationships 3.3.1 Error Identification
Fix:
good.html's equivalent card uses a real <button disabled> reading "Registration full" — native disabled removes it from the tab order and is exposed to AT as unavailable automatically, and its own visible text explains why, right on the control itself, not just in a nearby badge.

26. "Latest News"/"Trending" tabs aren't exposed as tabs at all, and the section has no heading of its own

Bad:
What used to be a single "Latest News" section is now two tabs built as plain <div>s with an onclick handler — no role="tablist", no role="tab", no aria-selected, no aria-controls, no role="tabpanel", and critically no tabindex at all, so a keyboard-only user cannot reach "Trending" no matter how they tab through the page. A screen reader has no way to know these are tabs, which one is selected, or that switching one changes what's below it. The section also lost its own heading: "Latest News" and "Trending" only exist as headings inside their own tab panel, so browsing by heading never surfaces a "News" label for the section as a whole — you only see one or the other, whichever panel happens to be open.
WCAG:
4.1.2 Name, Role, Value 2.1.1 Keyboard 1.3.1 Info and Relationships 2.4.6 Headings and Labels
Fix:
Not yet built for good.html.
